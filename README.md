# Audio Ninja

A native audio editor for macOS and iOS. Open a file, see it, play it, cut it.

Built with Swift 6.4 and SwiftUI, targeting macOS 27 and iOS 27.

## What it does

- Opens WAV, AIFF, CAF, MP3, M4A and FLAC
- Draws the waveform — one lane for the file by default, or one per channel if you turn on
  **Show Separate Channels** (⇧⌘L, or the ••• button)
- Click to place the cursor, drag to select. The cursor and both edges of a selection are labelled
  with their time, to the hundredth of a second. Play starts from the selection, or from the
  cursor, or from the beginning if neither is set
- **Trim to selection** and **delete selection**, with unlimited undo and redo
- After a cut, the original appears above the waveform with what was removed hatched out and its
  times listed, and a dashed marker shows where the waveform closed up. The selection and the
  playhead are shown on the original too. It stays until the next export, until the file is closed,
  or until you hide it; saving doesn't clear it, because both platforms save on their own seconds
  after every cut
- Saves every format it opens back in place, MP3 included. An M4A opened as Apple Lossless is
  saved as Apple Lossless; otherwise M4A means AAC
- **Export As** (the ••• menu, or File ▸ Export As on macOS) writes a copy as M4A, MP3, WAV, AIFF,
  FLAC or CAF

Editing is non-destructive. The decoded file is never modified; an edit list records which ranges
of it survive, so a cut is a few integers rather than a copy of the audio, and undo is effectively
free. Cut edges get a short raised-cosine ramp, because a butt splice between two samples that were
never adjacent is audible as a click.

## Layout

```
AudioNinja/                  SwiftUI views and the app scene
AudioNinjaShare/             iOS share extension (YouTube import; Debug and TestFlight only)
AudioNinjaYouTube/           iOS framework: YouTubeKit and the link parsing both of those share
Packages/AudioNinjaKit/      all the logic — audio, editing, the document model
scripts/                     project and app-icon generation, App Store upload
Support/                     Info.plist, entitlements and the icon master
```

The logic lives in a local Swift package so it builds and tests in seconds without Xcode, a
simulator or code signing. The app target is a thin UI shell on top.

## Building

```bash
# Logic tests — fast, no Xcode or simulator needed
swift test --package-path Packages/AudioNinjaKit

# The app
xcodebuild -project AudioNinja.xcodeproj -scheme AudioNinja -destination 'platform=macOS' build
xcodebuild -project AudioNinja.xcodeproj -scheme AudioNinja \
  -destination 'platform=iOS Simulator,name=iPhone 17' build
```

`AudioNinja.xcodeproj` is generated by `scripts/generate-xcodeproj.py`. The app's sources are a
file-system-synchronized folder, so adding a Swift file needs no project change. Regenerate only
when targets or build settings change.

`scripts/generate-app-icon.sh` rebuilds the app icon from `Support/AppIcon-Source-1024.png`;
run it after replacing that file.


## Developer builds: YouTube import

Neither feature below is in Release builds, which include App Store submissions and the GitHub
release: App Store Review Guideline 5.2.3 rejects apps that download media from YouTube. The Mac
command is in Debug builds only. The iPhone import is in Debug builds and in the **TestFlight**
configuration, which is Release plus the import, for internal TestFlight testers. Never submit a
TestFlight-configuration build for review or offer it to external testers, whose beta review
applies the same guidelines. Only download what you have the rights to: YouTube's terms of
service otherwise forbid it.

### iPhone and iPad: Import from YouTube, or Share ▸ Audio Ninja

In a Debug build run from Xcode, or a TestFlight-configuration build, there are two ways in:

- **Import from YouTube** on the launch screen (`AudioNinja/Views/YouTubeImportSheet.swift`):
  paste a video's link, or text containing one, and tap Import.
- **Share ▸ Audio Ninja** from the YouTube app, or a YouTube page in Safari. The share extension
  (`AudioNinjaShare/`) finds the stream and opens the app with an `audioninja://youtube-audio`
  link.

Either way, the video's M4A audio stream is found on the device with
[YouTubeKit](https://github.com/alexeichhorn/YouTubeKit) (local extraction only, so no
third-party server sees the video), in `AudioNinjaYouTube.framework`, which both use. The app
(`AudioNinja/Views/YouTubeShareReceiver.swift`) downloads the stream into **On My iPhone ▸ Audio
Ninja ▸ YouTube** and opens it, ready to cut and Export as MP3, WAV and the rest. It never
overwrites an earlier download, which may hold edits.

How Release leaves it out, all in `scripts/generate-xcodeproj.py`:

- The extension and framework targets still build, but Release excludes them from the app's
  link and embed phases and builds them unsigned. YouTubeKit is linked into the framework, not
  the app, because a package product linked into the app cannot be excluded this way: Xcode
  copies its resource bundle regardless.
- `YOUTUBE_SHARE`, defined for iOS in Debug and TestFlight only (`APP_YOUTUBE`), compiles the
  app's import button, receiver and YouTubeKit credit, and declares the `audioninja` URL scheme
  through the preprocessed Info.plist.

`CONFIGURATION=TestFlight scripts/upload-app-store.sh` uploads a build with the import; see
[RELEASING.md](RELEASING.md).

It is fragile by nature: YouTubeKit follows YouTube's undocumented internals and is pinned to
an exact version. When extraction starts failing, update `YOUTUBEKIT_VERSION`, regenerate the
project, and resolve packages.

The first run on a device needs Xcode to register the extension's App ID
(`com.simplepatrick.AudioNinja.Share`): automatic signing does this when you run the scheme.

### Mac: File ▸ Open YouTube URL…

Debug builds for macOS have **File ▸ Open YouTube URL…** (⇧⌘O). It downloads a video's audio
and opens it as a document, ready to cut and Export As. The default is M4A, YouTube's AAC
stream saved as is with no re-encode. MP3 and WAV are converted by ffmpeg.

It is compiled only into Debug macOS builds (`#if DEBUG && os(macOS)`).

One-time setup:

```bash
brew install yt-dlp ffmpeg
scripts/install-youtube-helper.sh   # again after editing scripts/youtube-audio.sh
```

The app is sandboxed, and a sandboxed process can't run yt-dlp itself. So the download is done
by `scripts/youtube-audio.sh`, which the app runs with `NSUserUnixTask` from
`~/Library/Application Scripts/com.simplepatrick.AudioNinja/`, outside the sandbox. Downloads
land in the app container's `Application Support/YouTube` folder; **Show Downloads** in the
window reveals it.

## Continuous integration

`.github/workflows/ci.yml` runs the logic tests and builds for macOS, the iOS Simulator and
iOS devices on every pull request into `main`. It also regenerates `AudioNinja.xcodeproj` and
fails if the result differs from what is committed, so the project file cannot drift from its
generator.

CI runs on the `xcode-27` runner image. `macos-latest` is macOS 26 with Xcode 26 and cannot
build this project, which needs the 27 SDKs and Swift 6.4.

Tagging `v*` publishes a macOS build to GitHub Releases — see [RELEASING.md](RELEASING.md),
which also covers what the published build is not (signed with a Developer ID, or notarized),
and what is still needed for TestFlight and the App Store.

## Notes

- **One third-party library: LAME, for MP3.** Apple ships an MP3 decoder but no encoder, so MP3
  is written by LAME 3.100, from the prebuilt, dynamic
  [LAME-xcframework](https://github.com/BB9z/LAME-xcframework) Swift package. LAME is LGPL. It
  ships unmodified as its own embedded framework and is credited, with its licence, under
  Acknowledgements in the app. Read [THIRD-PARTY-LICENSES.md](THIRD-PARTY-LICENSES.md) before
  changing how it is linked or adding another dependency.
- MP3 is saved at 192 kbit/s constant bitrate. It is lossy, so every save of an MP3 re-encodes it
  and loses a little more; for repeated editing, Export As WAV or FLAC first. MP3 is mono or
  stereo only, and rates MP3 can't express (96 kHz and the like) are resampled to 48 kHz or
  44.1 kHz.
- AAC supports a fixed set of sample rates; anything else (96 kHz and the like) is resampled to
  48 kHz or 44.1 kHz first. AAC export is mono or stereo only.
- Files are decoded fully into memory, with a 512 MB ceiling (~45 minutes of 48 kHz stereo).
  Longer files are refused with a clear message rather than risking an out-of-memory kill.
